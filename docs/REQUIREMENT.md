# MyTravelDex 요구사항 명세서

## 1. 문서 목적

새 표시명은 여행가봥이며 화면 초안은 `DISAN.md`를 따른다. 현재 앱은 기능 검증용 프로토타입이다. vNext는 Google 실제 지도+17개 시·도 GeoJSON, 하단 유지 작성 패널, 일방 팔로우·공개 프로필·방문 스탬프를 계획한다. 아래 신규 항목은 문서 계약이며 아직 구현·검증되지 않았다. 기존 저장·소유권·private/public 정책은 유지한다.

MyTravelDex는 사진과 위치정보를 기반으로 사용자의 여행 기록을 저장하고 지도에서 다시 탐색할 수 있도록 하는 서비스다. 본 문서는 백엔드 우선 MVP의 기능, 보안, 품질, 비용 요구사항을 정의한다.

## 2. 범위

### 2.1 기존 MVP 포함

- Google OAuth 로그인
- 사용자 프로필 생성 및 인증 사용자 식별
- 여행 기록의 생성, 조회, 수정, 삭제
- 여행 기록별 압축 보관 사진 및 썸네일 저장
- 사진 EXIF 기반 촬영일·GPS 추출 지원
- EXIF 누락 시 촬영일·위치 수동 입력
- 위도·경도 및 사람이 읽을 수 있는 장소명 저장
- 여행 기록의 `private`·`public` 공개 상태
- 본인 기록 전체 관리
- 공개 기록은 비로그인·로그인 사용자 모두 조회 가능
- 사용자의 소유권과 공개 상태에 따른 데이터·파일 접근 제어
- 웹과 Android에서 동일한 백엔드 계약 사용

### 2.2 이번 재설계 제외

- 상호 친구 승인, 댓글, 좋아요, 별도 스탬프 보상 아이템
- 프로필 사진 직접 업로드
- 링크 전용 공유
- 실시간 위치 추적 및 백그라운드 위치 수집
- 동영상 업로드
- 여행지 랜덤 추천 데이터베이스
- 시·군·구 이하 상세 행정구역 색칠 및 방문 보상
- 사진 자동 분류·얼굴 인식
- 여행 기록 PDF·앨범 자동 생성

## 4. 비기능 요구사항

### vNext UI·소셜 수용 기준의 상태

FR-UI-001~011, FR-PROFILE-001, FR-SOCIAL-001, FR-STAMP-001은 **계획됨·미구현/미실행**이다. 위 기존 기능 ID를 대체하거나 기존 실행 이력을 완료 처리하는 항목이 아니다. 신규 UI는 숫자 좌표 입력을 노출하지 않지만 내부 좌표 모델과 기존 API의 좌표 검증은 유지한다.

- 공개 프로필은 닉네임 1~30자(공백만 불가)·기본 아바타 또는 동의한 Google 사진이다. 공개 확인 전 기존 이름·사진을 자동 공개하지 않는다. 미설정 작성자는 기본 아바타·여행자로 표시하며 기록 작성을 막지 않는다. 이메일·Auth 메타데이터는 공개 응답에서 제외한다.
- 팔로우는 승인 없는 단방향 관계다. 자기 자신·중복 관계·타인 관계 변경을 차단한다. 관계 목록은 본인만 조회하며 공개 프로필만 검색한다. 닉네임 중복은 허용하고 사용자 ID로 구분한다.
- 홈 기본 범위는 본인의 complete(private 포함)와 팔로잉의 complete/public 합집합이다. 내 기록·친구·공개로 전환하고 비로그인은 공개 완료 기록만 탐색한다. 팔로우 해제가 상대의 public 정책을 바꾸지 않는다.
- 공개 프로필을 숨겨도 공개 기록을 비공개로 바꾸지 않으며 작성자 표시만 기본값으로 바꾼다. 기존 관계 해제는 가능하고 공개 프로필을 다시 확인하기 전 새 팔로우 대상 검색에서는 제외한다.
- Google 장소 검색·place_id 상세 조회·핀 보정의 역지오코딩은 서버를 통한다. 장소명·주소만 표시하고 오류 시 기존 확정 위치와 입력을 유지한다. 유효한 EXIF 위치로 저장하는 기존 흐름을 막지 않는다.

### 생성·편집·삭제 수용 기준

- 기간·대표 위치를 확정한 뒤 `draft`를 생성하고 업로드한다. 일반 목록은 `complete`만 표시하고 초안 복구 조회를 분리한다.
- 첫 사진은 네트워크 업로드 완료 순서가 아니라 사용자가 저장 전에 확정한 `display_order`의 첫 사진이다. 완료 후 순서 변경은 대표 위치·기간을 자동 변경하지 않는다.
- 완료 시 사진은 1~20장, 대표사진은 정확히 하나다. 미지정 시 첫 사진을 자동 선택한다. 마지막 사진 삭제는 거부하고 기록 전체 삭제를 안내한다.
- 완료·대표사진 교체·사진 삭제는 동일한 기록 잠금 아래 처리한다. 타인의 호출·직접 상태 변경·소유자 변경·다른 기록으로 사진 이동을 차단한다. 완료 재호출은 같은 완료 결과를 반환한다.
- 등록된 원본·썸네일의 직접 Storage 삭제·덮어쓰기를 차단한다. 기록·사진 삭제 시 파일 경로와 정리 작업을 DB 트랜잭션으로 먼저 보존한다.
- 정리 작업은 서버에서 재시도하며 이미 삭제된 파일은 성공으로 취급한다. 진행 중 업로드는 정리하지 않고, 취소·실패 후 남은 파일과 장기 미완료 초안도 추적한다.
- 공개 조회 제한은 서버에서 강제한다. 기본 테이블·관계 조회·공개 API·Storage 직접 요청 모두 동일한 공개 범위를 지켜야 한다.
- 공개 지도는 사용자가 확정한 대표 좌표를 제공한다. 원본은 소유자 전용이고 썸네일 URL은 서버가 권한과 최대 300초 만료를 검증한다. 비공개 전환은 신규 접근·발급을 막지만 이미 발급·저장된 파일의 즉시 회수는 보장하지 않는다.
- 새 위치는 생성자가 조회할 수 있고 공개 기록에 연결된 위치만 타인에게 공개한다. 공유 위치는 불변이며 보정 시 새 위치를 연결한다.

### MVP 제한값과 날짜 규칙

다음은 초기 MVP 기본값이며 변경 시 API·테스트를 함께 변경한다.

- 기록당 사진 1~20장, 선택 입력 파일당 최대 20 MiB, 허용 입력 MIME은 `image/jpeg`, `image/png`다. 미지원 형식은 선택 단계에서 안내한다.
- 입력 이미지는 최대 40메가픽셀, 썸네일은 JPEG·긴 변 최대 512px·최대 512 KiB다. 작은 이미지는 확대하지 않는다.
- 제목 최대 100자, 내용 최대 5,000자이며 PostgreSQL 문자 수 기준이다. 일일 업로드 횟수 제한은 MVP에서 두지 않고 파일·사진 수·사용량 알림으로 관리한다.
- EXIF 날짜는 촬영지 현지 달력 날짜를 집계한다. 오프셋이 없으면 원래 날짜를 유지하고 임의 UTC 변환을 하지 않는다. `captured_date`를 집계 기준으로 저장하고 시점을 확정할 수 없으면 `captured_at`은 null이다.
- 수동 기간·대표 위치가 자동 제안값보다 우선한다. 사진 추가·삭제·재정렬 후에는 저장된 기간·위치를 자동 덮어쓰지 않고 사용자가 재확정한다.

### 보안·개인정보

- 모든 소유자 전용 CRUD는 Supabase Auth 세션과 PostgreSQL RLS로 보호한다.
- Storage 파일 경로에는 인증 사용자 식별자를 포함한다.
- 공개 기록의 썸네일만 공개 응답에 포함하고 원본 파일은 인증 또는 짧은 만료시간의 signed URL로 제공한다.
- 공개 응답에서는 `photos`의 EXIF 정밀 좌표와 Storage 원본 경로를 제외한다. 소유자 조회에서만 필요한 메타데이터를 반환한다.
- Google OAuth Client Secret, Supabase service role key, 지도 서버 키는 클라이언트 번들에 포함하지 않는다.
- EXIF GPS는 위치 개인정보로 취급하고 수집·공개 목적을 사용자에게 안내한다.
- 서버 로그에 OAuth 토큰, 원본 이미지 URL, 불필요한 정밀 위치를 남기지 않는다.

### 신뢰성·성능

- 잘못된 인증·권한·입력은 안전한 오류 응답으로 처리한다.
- MVP에서는 Expo 클라이언트가 업로드 전에 사진을 압축하고 썸네일을 생성한다. 서버 측 이미지 처리는 후속 Edge Function 후보로 둔다.
- 목록 화면은 썸네일을 우선 사용하며 원본 다운로드를 강제하지 않는다.
- 이미지 업로드와 DB 저장 실패가 발생하면 고아 파일을 정리할 수 있어야 한다.
- 사진의 EXIF 날짜·위치가 없어도 사용자가 여행 시작일·종료일과 대표 위치를 입력하면 기록을 등록할 수 있어야 한다.
- 여러 사진의 유효한 촬영 날짜 중 최소·최대 날짜를 초깃값으로 제안하고 수동 보정된 최종 기간을 저장해야 한다.
- 첫 번째 사진에 위치가 없으면 다른 사진의 위치를 자동으로 대표 위치로 대체하지 않고 사용자에게 수동 위치를 요구해야 한다.
- 여행 기록은 사진, 여행 기간, 대표 위치가 저장되기 전에는 `complete` 상태로 전환되거나 공개 노출되지 않아야 한다.

### 호환성

- 백엔드는 웹과 Android 클라이언트에서 동일하게 사용한다.
- 웹에서 검증 가능한 UI·REST 흐름과 Android에서만 검증 가능한 권한·딥링크·센서 흐름을 분리한다.
- 추후 iOS 추가를 위해 플랫폼 종속 기능은 클라이언트 어댑터로 격리한다.

## 5. 권한 규칙

| 리소스 | 비로그인 | 로그인 사용자 | 소유자 |
|---|---:|---:|---:|
| 본인 프로필 | 불가 | 본인만 조회 | 본인 수정 |
| 공개 프로필 projection(vNext 계획) | 공개 확인된 ID·닉네임·아바타만 | 동일 | 본인 원본 프로필에서 수정 |
| 팔로우 관계(vNext 계획) | 불가 | 본인이 팔로워인 관계만 | 생성·해제, 타인 관계 변경 불가 |
| 비공개 여행 기록 | 불가 | 소유자만 | 조회·수정·삭제 |
| 공개 여행 기록 | `status = complete`인 기록만 조회 | `status = complete`인 기록만 조회 | 조회·수정·삭제 |
| 사진 파일 | 공개 상태와 파일 정책에 따름 | 허용 범위 내 조회 | 업로드·삭제 |

초기 구현에서는 완료된 공개 여행 기록과 연결된 썸네일만 공개 조회를 허용하고, 원본·EXIF 정밀 위치·모든 변경 작업은 소유자에게만 허용한다.

## 6. 비용 요구사항

- 개발 초기에는 Supabase Free 플랜 범위에서 동작해야 한다.
- 현재 계획 기준 무료 한도는 DB 500MB, Storage 1GB, Egress 5GB, MAU 50,000명 수준이며 실제 운영 전 요금표를 재확인한다.
- Google Maps Platform은 결제 계정과 사용량 관리가 필요하므로 API별 사용량 제한과 알림을 설정한다.
- 무료 한도 초과 시 자동으로 큰 비용이 발생하지 않도록 예산 알림과 사용량 모니터링을 둔다.
- 사진 크기·해상도·기록당 사진 수는 위 MVP 제한값을 적용한다.

## 7. 수용 기준

- 인증되지 않은 사용자는 소유자 전용 데이터를 조회·변경할 수 없다.
- 사용자는 다른 사용자의 비공개 여행 기록을 확인할 수 없다.
- 완료된 공개 여행 기록은 비로그인·로그인 사용자 모두 조회할 수 있고, 공개 응답에 원본 경로와 EXIF 정밀 위치가 포함되지 않는다.
- 다른 사용자는 자신의 ID로 타인의 전체 DB를 조회할 수 없고, 공개된 여행 기록과 연결된 데이터만 조회할 수 있다.
- 사진 메타데이터가 있으면 촬영일·위치가 저장되고, 없으면 수동 입력이 가능하다.
- 원본·썸네일 Storage 경로와 DB 레코드가 일관성을 유지한다.
- 핵심 권한·도메인 테스트가 통과한 후 웹·Android 검증을 진행한다.
- 사진이 없는 `draft`는 공개 목록·공개 상세에 노출되지 않는다.

## 9. 필요한 외부 API

MVP에서 활성화할 API는 다음과 같다.

- Maps JavaScript API: Expo Web 지도 표시와 스타일
- Maps SDK for Android: Android 네이티브 지도
- Maps SDK for iOS: 추후 iOS 지도
- Places API 또는 플랫폼별 Places SDK: 장소 검색과 장소명 보완
- Geocoding API: 좌표·주소 변환

초기 MVP에서는 Routes API, Navigation SDK, Roads API, Street View API, Static Maps API, Elevation API, Map Tiles API를 활성화하지 않는다.

## 10. 문서 변경 동기화

요구사항 변경은 다음 순서로 반영한다.

1. 이 문서에 요구사항 ID와 수용 기준을 변경한다.
2. `PRD.md`에 사용자 흐름·제품 정책·MVP 범위를 반영한다.
3. `TRD.md`에 데이터·API·RLS·환경변수·상태 전이를 반영한다.
4. `API_SPEC.md`와 `TEST_CASE.md`에 요청·응답·권한·검증을 반영한다.
5. `AGENTS.md`, `README.md`, `README.local.md`, `planning.md`의 범위·명령어·링크 영향을 확인한다.
6. `.env.example`의 키 추가·삭제·이름 변경 여부를 확인한다.
7. 구현 코드는 문서 동기화 검토가 끝난 후 수정한다.
