# MyTravelDex 요구사항 명세서

## 1. 문서 목적

MyTravelDex는 사진과 위치정보를 기반으로 사용자의 여행 기록을 저장하고 지도에서 다시 탐색할 수 있도록 하는 서비스다. 본 문서는 백엔드 우선 MVP의 기능, 보안, 품질, 비용 요구사항을 정의한다.

## 2. 범위

### 2.1 MVP 포함

- Google OAuth 로그인
- 사용자 프로필 생성 및 인증 사용자 식별
- 여행 기록의 생성, 조회, 수정, 삭제
- 여행 기록별 사진 원본 및 썸네일 저장
- 사진 EXIF 기반 촬영일·GPS 추출 지원
- EXIF 누락 시 촬영일·위치 수동 입력
- 위도·경도 및 사람이 읽을 수 있는 장소명 저장
- 여행 기록의 `private`·`public` 공개 상태
- 본인 기록 전체 관리
- 공개 기록의 비로그인 또는 로그인 사용자 조회 여부를 정책에 따라 분리 가능하도록 설계
- 사용자의 소유권과 공개 상태에 따른 데이터·파일 접근 제어
- 웹과 Android에서 동일한 백엔드 계약 사용

### 2.2 MVP 제외

- 친구, 팔로워, 댓글, 좋아요
- 링크 전용 공유
- 실시간 위치 추적 및 백그라운드 위치 수집
- 동영상 업로드
- 여행지 랜덤 추천 데이터베이스
- 행정구역 GeoJSON 기반 지도 색칠 및 진행도 계산
- 사진 자동 분류·얼굴 인식
- 여행 기록 PDF·앨범 자동 생성

## 3. 기능 요구사항

| ID | 요구사항 | 우선순위 | 완료 기준 |
|---|---|---:|---|
| FR-AUTH-001 | 사용자는 Google OAuth로 로그인할 수 있어야 한다. | Must | 인증 성공 후 서비스 사용자와 연결된다. |
| FR-AUTH-002 | 인증된 사용자는 자신의 프로필을 조회할 수 있어야 한다. | Must | 세션의 사용자 ID와 프로필 ID가 일치한다. |
| FR-TRAVEL-001 | 인증된 사용자는 여행 기록을 생성할 수 있어야 한다. | Must | 제목, 기록 내용, 여행일, 공개 상태가 저장된다. |
| FR-TRAVEL-002 | 사용자는 자신의 여행 기록만 수정·삭제할 수 있어야 한다. | Must | 다른 사용자 요청은 거부된다. |
| FR-TRAVEL-003 | 사용자는 자신의 여행 기록 목록과 상세를 조회할 수 있어야 한다. | Must | 비공개 기록을 포함해 본인 기록이 조회된다. |
| FR-TRAVEL-004 | 공개 여행 기록은 소유자가 아닌 사용자도 조회할 수 있어야 한다. | Must | `visibility = public`인 기록만 반환된다. |
| FR-TRAVEL-005 | 사용자는 여행 기록을 `private` 또는 `public`으로 설정할 수 있어야 한다. | Must | 허용된 두 값 이외는 저장되지 않는다. |
| FR-PHOTO-001 | 사용자는 여행 기록에 사진을 업로드할 수 있어야 한다. | Must | Storage 파일과 DB 메타데이터가 연결된다. |
| FR-PHOTO-002 | 원본 사진과 썸네일을 구분해 저장해야 한다. | Must | 각 사진에 원본·썸네일 경로가 존재한다. |
| FR-PHOTO-003 | 사진에서 추출한 EXIF 촬영일·GPS를 저장할 수 있어야 한다. | Must | 값이 없으면 null을 허용한다. |
| FR-PHOTO-004 | EXIF가 없는 경우 사용자가 날짜·위치를 입력할 수 있어야 한다. | Must | 수동 입력값이 최종 기록값으로 저장된다. |
| FR-LOCATION-001 | 여행 기록은 위도·경도와 선택적 장소명을 가질 수 있어야 한다. | Must | 위도·경도 범위가 검증된다. |
| FR-LOCATION-002 | 사용자는 지도에서 위치를 보정할 수 있어야 한다. | Should | 저장 전 좌표를 수정할 수 있다. |
| FR-MAP-001 | 지도 기능은 Google Maps Platform을 사용한다. | Must | 플랫폼별 지도 표시와 위치 선택이 가능하다. |

## 4. 비기능 요구사항

### 보안·개인정보

- 모든 소유자 전용 CRUD는 Supabase Auth 세션과 PostgreSQL RLS로 보호한다.
- Storage 파일 경로에는 인증 사용자 식별자를 포함한다.
- 공개 기록이라도 원본 파일과 썸네일 파일의 공개 범위는 동일한 정책을 적용한다.
- Google OAuth Client Secret, Supabase service role key, 지도 서버 키는 클라이언트 번들에 포함하지 않는다.
- EXIF GPS는 위치 개인정보로 취급하고 수집·공개 목적을 사용자에게 안내한다.
- 서버 로그에 OAuth 토큰, 원본 이미지 URL, 불필요한 정밀 위치를 남기지 않는다.

### 신뢰성·성능

- 잘못된 인증·권한·입력은 안전한 오류 응답으로 처리한다.
- 사진 원본은 업로드 전 또는 처리 과정에서 썸네일을 생성한다.
- 목록 화면은 썸네일을 우선 사용하며 원본 다운로드를 강제하지 않는다.
- 이미지 업로드와 DB 저장 실패가 발생하면 고아 파일을 정리할 수 있어야 한다.
- 날짜와 위치가 없는 사진도 기록 등록 자체는 실패하지 않아야 한다.

### 호환성

- 백엔드는 웹과 Android 클라이언트에서 동일하게 사용한다.
- 웹에서 검증 가능한 UI·REST 흐름과 Android에서만 검증 가능한 권한·딥링크·센서 흐름을 분리한다.
- 추후 iOS 추가를 위해 플랫폼 종속 기능은 클라이언트 어댑터로 격리한다.

## 5. 권한 규칙

| 리소스 | 비로그인 | 로그인 사용자 | 소유자 |
|---|---:|---:|---:|
| 본인 프로필 | 불가 | 본인만 조회 | 본인 수정 |
| 비공개 여행 기록 | 불가 | 소유자만 | 조회·수정·삭제 |
| 공개 여행 기록 | 조회 가능 여부는 공개 조회 정책에 따름 | 조회 가능 | 조회·수정·삭제 |
| 사진 파일 | 공개 상태와 파일 정책에 따름 | 허용 범위 내 조회 | 업로드·삭제 |

초기 구현에서는 공개 여행 기록과 연결된 사진만 공개 조회를 허용하고, 모든 변경 작업은 소유자에게만 허용한다.

## 6. 비용 요구사항

- 개발 초기에는 Supabase Free 플랜 범위에서 동작해야 한다.
- 현재 계획 기준 무료 한도는 DB 500MB, Storage 1GB, Egress 5GB, MAU 50,000명 수준이며 실제 운영 전 요금표를 재확인한다.
- Google Maps Platform은 결제 계정과 사용량 관리가 필요하므로 API별 사용량 제한과 알림을 설정한다.
- 무료 한도 초과 시 자동으로 큰 비용이 발생하지 않도록 예산 알림과 사용량 모니터링을 둔다.
- 사진 크기·해상도·업로드 횟수에 MVP 제한을 둔다.

## 7. 수용 기준

- 인증되지 않은 사용자는 소유자 전용 데이터를 조회·변경할 수 없다.
- 사용자는 다른 사용자의 비공개 여행 기록을 확인할 수 없다.
- 공개 여행 기록은 지정된 공개 정책에 따라 조회된다.
- 사진 메타데이터가 있으면 촬영일·위치가 저장되고, 없으면 수동 입력이 가능하다.
- 원본·썸네일 Storage 경로와 DB 레코드가 일관성을 유지한다.
- 핵심 권한·도메인 테스트가 통과한 후 웹·Android 검증을 진행한다.

## 8. 초기 설정 및 외부 서비스 요구사항

| ID | 요구사항 | 우선순위 | 완료 기준 |
|---|---|---:|---|
| FR-SETUP-001 | Supabase 프로젝트는 local·test·production 환경을 구분해야 한다. | Must | 환경별 URL, 키, DB를 혼용하지 않는다. |
| FR-SETUP-002 | PostgreSQL 스키마 변경은 migration으로 관리해야 한다. | Must | 원격 DB 변경 전에 migration 검토와 dry-run을 수행한다. |
| FR-SETUP-003 | Google OAuth는 Web·Android Client ID를 사용하고 추후 iOS Client ID를 추가할 수 있어야 한다. | Must | 환경별 Redirect URL이 등록되어야 한다. |
| FR-SETUP-004 | Google Maps API key는 플랫폼·API별 제한을 가져야 한다. | Must | 제한 없는 key를 사용하지 않는다. |
| FR-SETUP-005 | Google Maps 사용량과 비용 알림을 설정해야 한다. | Must | 비정상 호출과 예산 초과를 확인할 수 있다. |
| NFR-SECURITY-001 | 환경변수는 공개 클라이언트 값과 서버 전용 비밀값으로 분리해야 한다. | Must | service role key와 OAuth Secret이 앱 번들에 포함되지 않는다. |
| NFR-SECURITY-002 | 외부 API key는 애플리케이션 및 API 제한을 적용해야 한다. | Must | Web·Android·iOS·Server key가 분리된다. |
| NFR-OPERATIONS-001 | 외부 인증·지도·Storage 장애를 사용자 오류와 재시도로 처리해야 한다. | Must | `EXTERNAL_SERVICE_ERROR`와 재시도 흐름이 제공된다. |
| NFR-OPERATIONS-002 | 운영 전환 전에 무료 한도·비용·백업 정책을 확인해야 한다. | Must | Supabase와 Google Cloud 사용량 알림이 활성화된다. |
| NFR-DOCS-001 | 요구사항 변경 시 REQUIREMENT·PRD·TRD를 함께 갱신해야 한다. | Must | 문서 간 ID·용어·권한·API가 일치한다. |
| NFR-DOCS-002 | 환경변수 또는 외부 서비스 구성이 바뀌면 `.env.example`도 갱신해야 한다. | Must | TRD 환경변수 계약과 샘플이 동일하다. |

## 9. 필요한 외부 API

MVP에서 활성화할 API는 다음과 같다.

- Maps JavaScript API: Expo Web 지도 표시와 스타일
- Maps SDK for Android: Android 네이티브 지도
- Maps SDK for iOS: 추후 iOS 지도
- Places API 또는 플랫폼별 Places SDK: 장소 검색과 장소명 보완
- Geocoding API: 좌표·주소 변환

초기 MVP에서는 Routes API, Navigation SDK, Roads API, Street View API, Static Maps API, Elevation API, Map Tiles API를 활성화하지 않는다.

## 10. 문서 변경 동기화

요구사항 변경은 다음 순서로 반영한다.

1. 이 문서에 요구사항 ID와 수용 기준을 변경한다.
2. `PRD.md`에 사용자 흐름·제품 정책·MVP 범위를 반영한다.
3. `TRD.md`에 데이터·API·RLS·환경변수·테스트를 반영한다.
4. `AGENTS.md`의 명령어·보안·워크플로우 영향 여부를 확인한다.
5. `.env.example`의 키 추가·삭제·이름 변경 여부를 확인한다.
6. 구현 코드는 문서 동기화 검토가 끝난 후 수정한다.
